## Что это

Веб-приложение для управления задачами торговых агентов дистрибьютора косметики. Не CRM для сделок — задачник по клиентам-точкам (визиты, продажи, лист ожидания, задачи агенту).

**Стек**: Node.js без npm-зависимостей (без Express/React, всё вручную — роутер, multipart, zip), файловая БД `data/db.json` (JSON), scrypt для паролей. Фронтенд — vanilla JS/HTML/CSS, один файл `public/app.js`.

**Рабочая директория текущей сессии** (`/home/claude/crm-project`) — эфемерная песочница, не переживает сессию. Источник правды — переданный пользователю zip-архив и то, что он держит на своём GitHub (деплой на Render через GitHub Desktop). **Важно**: `data/db.json` НЕ переносится между пересборками (и в `.gitignore` — никогда не пушится на GitHub) — при новом архиве контрагенты создаются заново импортом, задачи и ручные правки клиентов иначе потерялись бы (см. кнопки экспорта ниже). **Именно поэтому любое тестирование в рабочей копии этой сессии — только на изолированной копии в `/tmp`, никогда напрямую на `data/db.json`** — см. «Технические заметки», критический урок 08.09.2026.

**Клиенты**: карточка точки — название, телефон (WhatsApp-иконка, нормализация номера — ведущий 0), адрес (ссылка «Карта» на 2ГИС), контактное лицо, **тип точки (Фаза 19: выпадающий список из 8 категорий — Салон красоты, Медицинский центр/клиника, Стоматология, Магазин, Спа-салон, Салон депиляции, Массажный салон, Другое; раньше был свободный текст с ~31 вариантом написания, при первом запуске на существующей базе значения автоматически мигрируют в канонический список)**, день визита, статус по договору (он же «работают по документам», см. Фазу 22), способ оплаты, Instagram (кликабельная ссылка вместо прежнего поля WhatsApp/соцсети), удобное время звонка, ЛПР, особые пожелания, окно приёма заявок, номер маршрута (ручное поле для порядка посещения — участвует в сортировке «Печать маршрута»), заметки. ИНН из карточки убран. **Права редактирования**: агент может редактировать ВСЕ поля карточки своих клиентов, кроме `ownerId` (переназначение ответственного) и пары служебных админ-флагов — это только админ/супервайзер. Точечного разрешения «может менять адрес/телефон» (было чекбоксом в «Команде») больше не существует — упразднено как избыточное после расширения прав агента. **Закрытие карточки свайпом вправо (Фаза 20)** — на сенсорных экранах, в дополнение к кнопке «Отмена»/клику вне модалки; не перехватывает свайп, начавшийся на чипах-фильтрах бренда/в календаре.

**Новая точка от агента → согласование супервайзера**: при создании клиента агентом карточка получает `pendingApproval: true` (в `src/api.js`), в списке — значок «на согласовании», в карточке — заметная плашка и кнопка «Одобрить точку» (видна админу/супервайзеру), на дашборде — счётчик «Новых точек на согласовании» (`pendingApprovalCount`). **С Фазы 23 на странице «Клиенты» есть отдельный фильтр-чекбокс «На согласовании»** (`onlyPendingApproval`, виден админу/супервайзеру) — показывает только такие карточки одним кликом.

**Артикул товара (Фаза 20)** — бейдж рядом с названием в регулярном/тестовом ассортименте и в «Последних продажах». Источник — `data/import/articles.json` (2182 позиции, нормализованное название → артикул), построен из 5 присланных прайс-листов поставщика (Чистовье/EPICA/Kapous+Studio+HY/Перчатки/Прочие ТД КМ, все `.xls`, сконвертированы через LibreOffice). Покрытие ~92% ассортиментных строк — не хватает прайса на 5-й бренд (AV/ES/PRO/MS, декоративная косметика) и есть промахи на нетиповых/обрезанных названиях; для них бейдж просто не показывается.

**«Последние продажи» (Фаза 20)** — новый раздел карточки клиента, по образцу регулярного/тестового ассортимента. В исходных данных НЕТ номеров/дат отдельных накладных (только помесячные суммы по товару) — раздел честно показывает последние 3 месяца, где у клиента были продажи (не обязательно подряд), с товаром/кол-вом/ценой за штуку. Источник данных — уже существующий `client.monthlyAssortment` (Фаза 6.2), никаких новых бэкенд-эндпоинтов не потребовалось.

**Загрузка долгов через панель (Фаза 19)** — на странице «Команда» (только администратор) кнопка «⬆ Загрузить долги», принимает `.xlsx` или `.csv` (свой ридер в `src/fileTable.js` — ZIP+XML для xlsx через встроенный `zlib`, без внешних библиотек; старый `.xls` не поддержан — нет LibreOffice на сервере). Колонки ищутся по синонимам заголовка (`findColumn`/`DEBT_*_ALIASES` в `src/api.js`), при несовпадении заголовков — понятная ошибка со списком найденных колонок, а не молчаливое угадывание. Эндпойнт — **полная замена снимка** (клиент не из нового файла → долг обнуляется, это «срез на дату», не баг), пишет результат в `data/import/debts.json` на диск (переживает перезапуск) и пересчитывает уже сохранённые поля клиентов на лету, без полного реимпорта. Долг по-прежнему сопоставляется с клиентом только по имени (без агента) — по явному решению пользователя это не стали чинить заодно. **Парная кнопка «⬆ Загрузить остатки» (была тут же, для запаса на складе) убрана в Фазе 24 (09.09.2026) вместе со всей фичей «Остаток» — см. Фазу 24 выше.**

Таблица «Клиенты»: колонки в порядке Название → Номер телефона → Адрес → Контактное лицо → Тип точки → Маршрут № → План → Продано в этом месяце → Долг → Недопродано; **с Фазы 24 колонка «Продано в этом месяце» кликабельна для сортировки** (`data-sort="sales"`, по `currentMonthRevenue`), как «Маршрут №»/«Долг»/«Недопродано», и заголовок статичный (без названия месяца — раньше был «Продано (Месяц)»). Фильтры: день визита, тип точки, «постоянный клиент», задолженность, способ оплаты, «недопродано», «на согласовании» (Фаза 23), по агенту (у супервайзера — есть), текстовый поиск (Фаза 21: можно печатать полностью, не кликая заново после каждой буквы). **Фильтр «Есть акции» и бейдж 🎁 убраны в Фазе 24** вместе со всей фичей акций.

**Ассортимент клиента — логика с 02.09.2026 (Фаза 18, ПОЛНОСТЬЮ заменяет всё, что было раньше, включая формулировку от 01.09.2026 — если в старой переписке встретится «3 из 5 месяцев» или «разрыв ≤2», это уже не актуально)**: регулярный ассортимент товара — куплен **в обоих последних 2 месяцах** окна (подтверждает, что берут прямо сейчас) **И** минимум в **4 из последних 6 месяцев** окна (подтверждает, что покупка не разовая). Окно динамическое — всегда последние 6 из тех месяцев, что реально есть в данных (сейчас март–август); при появлении нового месяца продаж окно сдвинется само на следующей пересборке, это НЕ завязано на системную дату сервера. Тестовый ассортимент — куплен в окне хотя бы раз, но не прошёл эти условия. Товар, ни разу не купленный в окне (даже если покупался раньше) — не попадает ни в тот, ни в другой список. На реальных данных новое правило заметно строже старого: 502 позиции / ~161–164 клиента (было 1309/303 по правилу «3 из 5 + разрыв ≤2») — целенаправленно, чтобы в регулярном ассортименте оставалось только то, что клиент покупает прямо сейчас на постоянной основе, а не то, что покупал часто когда-то.

«Недопродано» (atRisk, Фаза 18) — переопределено: постоянный ассортимент МИНУС то, что уже куплено в текущем месяце (а не «не куплено в последнем месяце окна классификации», как было раньше) — явный фокус на допродажу регулярного ассортимента. Технически считается не при импорте, а динамически при КАЖДОЙ отдаче клиента (`computeAtRisk()` в `src/api.js`, вызывается из `withFreshCurrentMonth()`) — сверяет `regularAssortment` с `currentMonthItems` (отдельный поток «продажи текущего месяца», тот же что питает карточки дашборда). Плюс: обновляется сразу при загрузке свежего среза продаж текущего месяца, не дожидаясь полной пересборки всего 6-месячного ассортимента. Пока новый месяц не прислан (см. «протухание» ниже) — весь постоянный ассортимент честно показывается как «недопродано» (currentMonthItems пуст) — это корректно: в начале месяца ещё ничего не продано, ничего скрывать не нужно (раньше в этой ситуации флаг наоборот принудительно обнулялся до фактических данных — так уже не делаем). Краски/оксиды — отдельная группа в обычном списке, не в «недопродано»; в карточке клиента (и в регулярном, и в тестовом ассортименте отдельно) есть переключатель «Убрать краски/оксиды», прячущий эту группу независимо от выбранного бренда. Отдельно — помесячная детализация (`monthlyAssortment`) для фильтра по конкретному месяцу в отчётах/рейтинге клиентов (не менялась, всё ещё 7 месяцев данных целиком). **Бейдж «Остаток на складе» (📦, срез на дату) на позициях ассортимента убран в Фазе 24** — см. выше; backend по-прежнему считает `stockQty`/`stockUnit` при импорте (`attachStock()` в `src/import.js`), просто фронтенд их больше не показывает. **С Фазы 27 (11.09.2026) позиции регулярного ассортимента, уже купленные в этом месяце (`atRisk: false`), помечены в общем списке зелёным бейджем «оформлено»** — чтобы отличать от «Недопродано» с первого взгляда, не открывая отдельно «Последние продажи»; у тестового ассортимента бейджа нет (там нет самого понятия «недопродано»).

«Постоянный клиент» (отдельная client-level метка, не путать с регулярным ассортиментом по товару) — купил что-либо (любой ассортимент) 3 календарных месяца подряд. Не менялась в Фазе 18.

Данные текущего месяца (`currentMonthRevenue`/`currentMonthItems`) автоматически обнуляются на дашборде/в API, пока новый месяц не подтверждён и не пересчитан целиком (см. `isCurrentMonthDataFresh()`/`CURRENT_MONTH_DATA_STALE_FROM` в `src/api.js`) — сам список regularAssortment/testAssortment при этом НЕ обнуляется (это историческая статистика, актуальна независимо от календаря). «Недопродано» теперь вычисляется ПОСЛЕ этого обнуления (а не обнуляется отдельным принудительным флагом, как раньше) — см. абзац выше. **С Фазы 22 в дашборде — срез за сентябрь** (изначально частичная неделя 01.09–07.09.26, растёт по мере новых выгрузок — пользователь явно выбрал загружать как срез, не дожидаясь конца месяца); `CURRENT_MONTH_DATA_STALE_FROM` = 1 октября — сдвигать вперёд только когда сентябрь закроется целиком. **Акции (`promotions`) убраны в Фазе 24** — раньше устраивались так же (пересчитывались целиком из `data/import/promotions.json` при каждом импорте, гасли по той же «протухшей» логике) — теперь `withFreshCurrentMonth()` всегда отдаёт `promotions: []`, независимо от свежести.

**Бренды** (переопределены 01.09.2026): 5 актуальных — EPICA (префикс «E »), Kapous (префикс «HY »), Studio (префикс «S », отдельный от Kapous), AV/ES/PRO/MS (составное имя-плейсхолдер для 4 латинских префиксов av/es/pro/ms — пользователь попросил объединить их в один новый бренд и явно согласовал именно такое имя), Чистовье (всё остальное без латинской буквы в начале названия). Плюс историческая Палитра (не трогалась) и почти пустой «Прочее» (единицы позиций, где даже с латинской буквы бренд не опознан — сознательно не гадаем). Определяется по ключевым словам/префиксам в названии товара (`brand_tagging.py` в `/home/claude/gdrive-data/`), в источнике нет отдельного столбца бренда.

**Задачи — 4 независимые воронки**:
- «Визиты с супервайзером» — В работе → Выполнена (подтверждает супервайзер, этап «Архив») / Не выполнена, теги брендов + Лист ожидания/Прогрев как теги. **Фаза 23**: время визита стало диапазоном — `visitTime` («от») + новое `visitTimeTo` («до»), на карточке показывается как «ЧЧ:ММ–ЧЧ:ММ».
- «Продажа» (Фаза 22, ПОЛНОСТЬЮ переделана — если в старой переписке встретится «Звонок → Встреча → Сделка/Провал», это уже не актуально) — технически устроена точно так же, как визит: те же этапы В работе / Выполнена (обязателен отчёт) / Не выполнена / Архив, свой набор тегов (бренды + «Договор»). Больше нет обязательного пояснения/аудиозаписи встречи перед закрытием. Перевод в «Не выполнена» выгружается опционально в Google Таблицу (код готов, сервисный аккаунт не настроен) — было завязано на этап «Провал», теперь на «Не выполнена».
- «Лист ожидания» — Клиент ждёт товар → Накладная оформлена → Товар получен (подтверждает супервайзер), свои теги брендов.
- **«Задачи агенту» (Фаза 23, новое) — без привязки к клиенту** (`taskType: 'agent'`, `clientId: null`). Общие этапы, что и у визита, отчёт, вложения, заявка на перенос даты — но без клиента/тегов/времени визита. Для поручений вроде «сдать отчёт»/«забрать образцы», не относящихся к конкретной точке. Единственный тип задачи, доступный даже в системе без единого клиента.

**Смена воронки (Фаза 23, права расширены в Фазе 24)**: у уже созданной задачи-визита/продажи/листа ожидания можно сменить `taskType` прямо в карточке (отдельный select «Воронка», применяется сразу отдельным запросом) — этап/теги, недопустимые в новой воронке, сбрасываются автоматически. Изначально (Фаза 23) было доступно только администратору/супервайзеру; **с Фазы 24 (09.09.2026) доступно любому, у кого вообще есть право редактировать эту задачу — включая самого агента на своей задаче** (пользователь явно попросил убрать необходимость обращаться к супервайзеру за каждой сменой воронки). «Задачи агенту» в эту смену не входят (нет клиента для перехода в обратную сторону).

**Фильтры на странице «Задачи» (Фаза 23)**: поиск клиента (по имени/телефону, для задач без клиента — по названию задачи), общий для всех 4 воронок; чекбокс «Есть заявка на перенос даты» (поверх `dateChangeRequest`), тоже общий для всех воронок — бейдж заявки теперь показывается одинаково на всех досках, а не только на «Продажах».

Даты задач — кастомный виджет ДД.ММ.ГГ с мини-календарём. Телефон клиента виден на карточках задач во всех воронках. Заявка на перенос даты — если срок уже установлен, агент отправляет заявку, супервайзер одобряет/отклоняет. **Поиск клиента при выборе его в форме — над `<select>` есть текстовое поле, сужающее список по подстроке в названии (без учёта регистра); сам `<select>` остаётся источником истины при отправке формы.** Реализовано в двух местах через общую функцию `wireClientSearchSelect()` (Фаза 18 — «Новая задача», Фаза 26 — «Встреча с клиентом» в Календаре, см. выше). При создании новой задачи поле поиска есть; при РЕДАКТИРОВАНИИ существующей задачи клиент намеренно заблокирован (менять его нельзя) — поля поиска там нет по замыслу, не баг.

**Дашборд**: сводные карточки с фильтром по агенту (клиенты, задачи сегодня, просрочено, недопродано) и по способу оплаты (долг) — оба фильтра-селекта компактного размера. (Плавающая кнопка «⬆ Наверх» была добавлена в Фазе 17 и полностью убрана в Фазе 18 — пользователь передумал сразу после сдачи, в коде её больше нет.) Дашборд агента — «Мои показатели»: «**Продано в этом месяце**» (Фаза 24, была подпись с названием месяца), снизу чипы-фильтр по месяцам для «Продано всего» (любая комбинация — сумма и разбивка по клиентам через «/» пересчитываются на лету); топ-10 товаров по брендам (без красителей/оксидов у Kapous/EPICA); «Продаж сегодня»/«Из них закрыто» (Фаза 22, было «звонков»/«встреч» — не подходит к упрощённой воронке продаж). Рейтинг клиентов супервайзера (выручка/маржа/активность, фильтр по агенту и месяцу). **Карточка «Клиентов с акциями» на дашборде агента и панель «🎁 Акции (вся команда)» на дашборде супервайзера убраны в Фазе 24.**

**Календарь**: месяц/неделя/день; встречи супервайзера с клиентом (лёгкая «бронь дня», выбор клиента — с поиском по имени, см. Фазу 26 выше); печать маршрута на неделю (супервайзер) — список по агентам/дням, точки внутри дня сортируются по «Номеру маршрута» клиента по возрастанию (у кого не проставлен — в конце, в исходном порядке).

Отдельный трёхпозиционный переключатель «Все категории / Только краски-оксиды / Убрать краски-оксиды» сочетается с выбором бренда — например, Kapous + «Только краски/оксиды» покажет краски/оксиды именно у Kapous. **Отдельный отчёт «Акции» убран в Фазе 24** вместе со всей фичей акций (был: фильтр по агенту, бейдж «🎁 акции» у клиента в списке, фильтр «Есть акции»).

Единственное реальное ролевое ограничение — агент видит и правит только свои задачи (но с Фазы 24 в рамках своей задачи может сам сменить и её воронку — см. выше).

**Экспорт/бэкап**:
- «Выгрузить клиентов» / «Загрузить клиентов» (страница «Команда», только админ) — пара кнопок для переноса ручных правок между пересборками. «Выгрузить» — JSON со всеми РУЧНЫМИ/бизнес-полями клиентов (адрес, телефон, конт.лицо, договор, оплата, номер маршрута, заметки, мастера, статус закрытия и т.п.), без пересчитываемых полей (ассортимент/долг/продажи месяца — они и так пересчитываются заново из файлов продаж при каждой пересборке). «Загрузить» — обратная загрузка такого файла: находит существующего клиента по имени+агенту и обновляет его ручные поля; **с Фазы 28 (11.09.2026) клиента, которого не нашёл (например, заведённого агентом самостоятельно и потому отсутствующего в свежепересобранной базе), создаёт заново с теми же ручными полями**, а не молча пропускает — дублей всё равно не бывает, повторная загрузка того же файла безопасна.
- «Выгрузить задачи» / «Загрузить задачи» (вкладка «Задачи») — экспорт/импорт задач для переноса между месяцами/пересборками (человекочитаемые имена клиента/агента, без вложений). Импорт корректно конвертирует старые/отменённые значения `stage` в актуальную схему (Фаза 22) и теперь (Фаза 23) корректно восстанавливает и задачи-агенту без клиента.
- Полный бэкап (Команда, только админ) — весь `db.json` + вложения, zip.
- CSV клиентов (супервайзер) — актуальный набор колонок.

**Прочее**: массовая перепривязка клиентов, push-уведомления (только при открытой вкладке, не настоящий web-push), «точка закрыта» — запрос агента + подтверждение супервайзера, журнал заметок по звонкам отдельно от задач, мастера точки (модель данных + карточка).

## Известные ограничения

- Регулярный ассортимент/недопродано считаются помесячно (не по дням) — приближение (см. логику выше).
- Способ оплаты и статус «по договору» (104 клиента «да», Фаза 11+22) — есть не у всех клиентов (нет источника в исходных таблицах, часть не сопоставилась автоматически по названию).
- Обновление продаж/ассортимента — по-прежнему не автоматическое, только через новую сессию с Claude и пересборку архива (нужен полный Python-пайплайн; пользователь явно подтвердил в Фазе 23 п.9, что это устраивает — автоматическое подхватывание новых клиентов делать не будем). Долги — исключение с Фазы 19: обновляются прямо через панель «Команда» (см. выше), без сессии и без пересборки, но только если файл в `.xlsx`/`.csv` (парная загрузка остатков убрана в Фазе 24). Ручные правки клиентов, включая клиентов, заведённых агентами самостоятельно, можно сохранить через «Выгрузить клиентов» и передать в следующую сессию (а при следующей пересборке сразу же и загрузить обратно через «Загрузить клиентов» — с Фазы 28 эта кнопка восстанавливает и самостоятельно заведённых клиентов, а не только правки к уже существующим; но это работает только если экспорт сделан ДО начала пересборки — данных для восстановления иначе просто не будет).
- Бренд товара определяется по ключевым словам/латинским префиксам в названии (не по отдельному столбцу) — Палитра осознанно не трогалась, единичные «Прочее»-позиции не гадаем.
- На бесплатном тарифе Render данные не гарантированно сохраняются между перезапусками — нужен платный план с постоянным диском; есть кнопка ручного бэкапа.
- Нет смены пароля из интерфейса, нет email/SMS-уведомлений.
- Файловая БД рассчитана на команду до ~10-15 активных пользователей.
- Артикул товара проставлен не у всех позиций (~92%, см. выше) — нет прайса на бренд AV/ES/PRO/MS.
- «Последние продажи» на карточке клиента — это последние 3 месяца с продажами, не настоящие накладные (см. выше).
- **Данные текущего месяца сопоставляются с клиентом только по имени, без учёта агента** — если одно имя (например «Частное лицо») встречается как клиент у нескольких разных агентов, все получают одну и ту же объединённую сумму (та же логика, что у долгов). Обнаружено при загрузке сентябрьского среза (Фаза 22) — сознательно не стали чинить заодно.

## Как работать с этим пользователем

- Присылает правки списком, по одной, ожидая, что каждая будет зафиксирована перед реализацией; даёт финальный сигнал фразой вроде «делай правки» / «делаем» / «делай все правки N» / «всё, я закончил» / «делай все правки в коде» / «сделай все правки». **Не все правки идут через бэклог** — Фаза 24 показала, что короткие прямые сообщения («в дашборде окно продано август измени на продано в этом месяце», «не смог поменять воронку по задаче сделай возможность смены воронки без запроса каждому агенту», «убери остаток кол-во везде где он есть он больше не нужен», «убери акции по клиентам текущие показатели этого месяца», «в клиенты добавь возможность сортировки по продаже за сентябрь») тоже штатный формат: это не бэклог-пункты для фиксации, а команда на немедленную реализацию, без «делай правки» на отдельной строке. **В Фазе 24 несколько таких сообщений пришли одно за другим в течение нескольких минут, некоторые — прямо во время выполнения предыдущего** (харнесс доставляет их как «пользователь написал, пока ты работал») — не откладывать, а поставить в очередь и обработать по порядку, не теряя ни одного и не прерывая уже начатое на середине.
- **Слово «запиши»** (Фаза 24) — используется как самостоятельная короткая реплика вслед за только что данным поручением. По контексту — это не отмена/не блокировка реализации, а напоминание не забыть задокументировать (в духе правила «после каждого раунда правок обновлять документацию» ниже) — реализация продолжается, документация просто ведётся тщательнее в ответ на это слово.
- **Короткое сообщение с жалобой на баг может описывать место неточно** (Фаза 26: «если выбирать клиента в задачах то нет подбора по имени» — фактически имелась в виду не форма задачи, а форма встречи супервайзера в Календаре, где действительно не было поиска). Первая реакция — не переспрашивать вслепую, а сначала проверить БУКВАЛЬНО названное место на живом тестовом сервере; если там всё работает корректно — искать похожие места в интерфейсе (тот же паттерн, тот же тип поля), где бага теоретически можно ожидать, и только если несколько кандидатов — задать один точный уточняющий вопрос с конкретными вариантами (через AskUserQuestion), а не гадать или спрашивать расплывчато «где именно?».
- Явно просит уточнять, если что-то непонятно («если нужно уточняй, пока не получится то, что нужно») — не гадать, особенно про смысл сокращений/префиксов в названиях товаров и про пороги бизнес-логики. Если буквальная реализация правила даёт статистически странный результат (пример: Фаза 16 п.11 — правило «пауза ≤2 месяца» без минимума по числу покупок дало 39% «регулярных» позиций с одной покупкой за 5 месяцев) — показать пользователю конкретные цифры и предложенный вариант через AskUserQuestion, а не тихо доносить как есть.
- Для больших пакетов правок — сначала уточняющие вопросы через быстрый выбор (AskUserQuestion), затем при необходимости визуальный макет до кода. **Для маленьких точечных правок (Фаза 24) уточняющие вопросы не нужны** — если формулировка ясна («продано в этом месяце» вместо «продано (месяц)», «убери X, он больше не нужен»), сразу применять по всем явно названным местам, без AskUserQuestion — даже когда объём фактической работы (найти все места в коде) оказывается не таким уж и «точечным» (пример: «акции» задели 6+ мест в двух файлах).
- Если в одном вопросе несколько под-пунктов — обычно отвечает свободным текстом только на один; на остальное лучше сделать разумное предположение по умолчанию, явно написать о нём и продолжать, а не переспрашивать бесконечно.
- Часто присылает исходные файлы не сразу, а через сообщение-два после того, как узнаёт про ограничение («такого-то поля нет в данных») — реагировать сбором/парсингом файла сразу же, без дополнительных уточнений по формату, если он в целом похож на прежние источники.
- Часто присылает несколько разнородных поручений одним сообщением или короткой серией сообщений вперемешку с промежуточными уточнениями («запиши») и без чёткой границы между поручениями (Фаза 24: «продано в дашборде» → «запиши» → «и в карточке контрагента тоже» → «запиши» → «не смог сменить воронку, разреши агентам» → «сделай все правки» → «убери остаток» + «убери акции» + «запиши» одним сообщением из трёх строк → «добавь сортировку по сентябрю», последнее — уже во время работы над предыдущими) — не теряя ни одного пункта, разобрать по отдельности, картировать зависимости между ними и подтверждать выполнение каждого явно в финальном ответе, а не молча.
- После деплоя может вернуться с вопросом «почему X не работает/не грузится» по конкретному файлу или экрану — не ограничиваться словесным объяснением: воспроизвести проблему на тестовом сервере, найти точную причину (в Фазе 24, п.2 — это было не баг, а сознательное ограничение прав в коде Фазы 23, которое пользователь счёл слишком строгим; в Фазе 26 — жалоба оказалась про другое, похожее место в интерфейсе, а не про то, что было названо буквально) и подтвердить фактическим прогоном (curl/API/Playwright), а не только теорией.
- **Иногда присылает большой список правок явно ПОМЕЧЕННЫЙ как бэклог, не как команду на реализацию** (Фаза 22, 10 пунктов, заголовок «пока не в работе», явная фраза «не приступать без отдельной команды») — в таком случае НЕ начинать реализацию, только зафиксировать в проектных документах и подтвердить пользователю, что список сохранён и ждёт команды. Может затем вернуться коротким сообщением с уточнениями — это тоже НЕ команда на реализацию сама по себе, пока не придёт отдельный явный сигнал («делай все правки в коде»). **Фаза 24 показала другой, гораздо более частый режим — короткие прямые правки БЕЗ предварительного бэклога** — не путать эти два режима: если сообщение уже содержит конкретное «сделай X»/«убери Y» без пометки «в очередь»/«не начинай» — это сразу команда на реализацию.
- Деплой — через GitHub Desktop (Clone → скопировать файлы → Commit → Push), инструкции давать по одному шагу, ждать «готово».
- После каждого раунда правок, включая маленькие точечные (Фаза 24 подтвердила: масштаб правки не повод пропускать): обновить README проекта, обновить статус-документ в проекте «црм » (`claude/crm-mvp-status.md`), обновить и этот файл при значимых изменениях, пересобрать zip, проверить чистую установку (импорт с нуля + curl-проверка ключевых изменений), отправить архив.

Вынесен в `wireClientSearchSelect(searchInputId, selectId, clients)` — принимает ID полей и список клиентов, ничего специфичного для задач внутри не осталось. При добавлении в будущем ЕЩЁ одной формы с длинным `<select>` клиентов (в проекте это распространённый паттерн — модалки с выбором клиента встречаются в нескольких местах) — сначала проверить, использует ли она уже эту функцию, и если нет, подключить её тем же способом (текстовый инпут `id="..."` над `<select id="...">`, дальше один вызов `wireClientSearchSelect(...)` после вставки формы в DOM), а не копировать логику фильтрации заново.
- **Бейдж «оформлено» на уже купленных в этом месяце позициях регулярного ассортимента (Фаза 27, 11.09.2026)** — добавлен прямо в `assortRow()` (`public/app.js`), общей для регулярного/тестового ассортимента и «Недопродано»; условие `p.atRisk === false` (поле есть только у регулярного ассортимента, см. `computeAtRisk()`) — при добавлении новых типов позиций с похожим статусом ориентироваться на этот же паттерн (поле на самой позиции + условный бейдж в общей функции рендера строки), а не заводить отдельную функцию рендера.
