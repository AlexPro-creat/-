# Задачник для торговых агентов — краткая справка для нового диалога

Дата: 2026-09-04. Это сжатая версия статуса проекта — только то, что нужно, чтобы Claude в новом окне сразу понимал текущее состояние. Полная история по фазам (1–20) — в документе проекта «црм » (`claude/crm-mvp-status.md`), там же все технические детали реализации и код.

## Что это

Веб-приложение для управления задачами торговых агентов дистрибьютора косметики. Не CRM для сделок — задачник по клиентам-точкам (визиты, продажи, лист ожидания).

**Стек**: Node.js без npm-зависимостей (без Express/React, всё вручную — роутер, multipart, zip), файловая БД `data/db.json` (JSON), scrypt для паролей. Фронтенд — vanilla JS/HTML/CSS, один файл `public/app.js`.

**Рабочая директория текущей сессии** (`/home/claude/crm-project`) — эфемерная песочница, не переживает сессию. Источник правды — переданный пользователю zip-архив и то, что он держит на своём GitHub (деплой на Render через GitHub Desktop). **Важно**: `data/db.json` НЕ переносится между пересборками — при новом архиве контрагенты создаются заново импортом, задачи и ручные правки клиентов иначе потерялись бы (см. кнопки экспорта ниже).

## Текущий функционал (консолидированно, без фазовой истории)

**Клиенты**: карточка точки — название, телефон (WhatsApp-иконка, нормализация номера — ведущий 0), адрес (ссылка «Карта» на 2ГИС), контактное лицо, **тип точки (Фаза 19: выпадающий список из 8 категорий — Салон красоты, Медицинский центр/клиника, Стоматология, Магазин, Спа-салон, Салон депиляции, Массажный салон, Другое; раньше был свободный текст с ~31 вариантом написания, при первом запуске на существующей базе значения автоматически мигрируют в канонический список)**, день визита, статус по договору, способ оплаты, Instagram (кликабельная ссылка вместо прежнего поля WhatsApp/соцсети), удобное время звонка, ЛПР, особые пожелания, окно приёма заявок, номер маршрута (ручное поле для порядка посещения — участвует в сортировке «Печать маршрута»), заметки. ИНН из карточки убран. **Права редактирования**: агент может редактировать ВСЕ поля карточки своих клиентов, кроме `ownerId` (переназначение ответственного) и пары служебных админ-флагов — это только админ/супервайзер. Точечного разрешения «может менять адрес/телефон» (было чекбоксом в «Команде») больше не существует — упразднено как избыточное после расширения прав агента. **Закрытие карточки свайпом вправо (Фаза 20)** — на сенсорных экранах, в дополнение к кнопке «Отмена»/клику вне модалки; не перехватывает свайп, начавшийся на чипах-фильтрах бренда/в календаре.

**Артикул товара (Фаза 20)** — бейдж рядом с названием в регулярном/тестовом ассортименте и в «Последних продажах». Источник — `data/import/articles.json` (2182 позиции, нормализованное название → артикул), построен из 5 присланных прайс-листов поставщика (Чистовье/EPICA/Kapous+Studio+HY/Перчатки/Прочие ТД КМ, все `.xls`, сконвертированы через LibreOffice). Покрытие ~92% ассортиментных строк — не хватает прайса на 5-й бренд (AV/ES/PRO/MS, декоративная косметика) и есть промахи на нетиповых/обрезанных названиях; для них бейдж просто не показывается.

**«Последние продажи» (Фаза 20)** — новый раздел карточки клиента, по образцу регулярного/тестового ассортимента. В исходных данных НЕТ номеров/дат отдельных накладных (только помесячные суммы по товару) — раздел честно показывает последние 3 месяца, где у клиента были продажи (не обязательно подряд), с товаром/кол-вом/ценой за штуку. Источник данных — уже существующий `client.monthlyAssortment` (Фаза 6.2), никаких новых бэкенд-эндпоинтов не потребовалось.

**Загрузка долгов/остатков через панель (Фаза 19)** — на странице «Команда» (только администратор) две кнопки «⬆ Загрузить долги» / «⬆ Загрузить остатки», принимают `.xlsx` или `.csv` (свой ридер в `src/fileTable.js` — ZIP+XML для xlsx через встроенный `zlib`, без внешних библиотек; старый `.xls` не поддержан — нет LibreOffice на сервере). Колонки ищутся по синонимам заголовка (`findColumn`/`*_ALIASES` в `src/api.js`), при несовпадении заголовков — понятная ошибка со списком найденных колонок, а не молчаливое угадывание. Оба эндпойнта — **полная замена снимка** (клиент не из нового файла → долг/остаток обнуляются, это «срез на дату», не баг), пишут результат в `data/import/debts.json`/`stock.json` на диск (переживает перезапуск) и пересчитывают уже сохранённые поля клиентов на лету, без полного реимпорта. Долг по-прежнему сопоставляется с клиентом только по имени (без агента) — по явному решению пользователя это не стали чинить заодно. Дата «снято на» для остатков теперь берётся из `db.getSetting('stockAsOf', ...)` и обновляется датой сервера при каждой загрузке (раньше — захардкожена в `STOCK_AS_OF`).

Таблица «Клиенты»: колонки в порядке Название → Номер телефона → Адрес → Контактное лицо → Тип точки → Маршрут № → План → Продано (месяц) → Долг → Недопродано. Фильтры: день визита, тип точки, «постоянный клиент», задолженность, способ оплаты, «недопродано», «есть акции», по агенту (у супервайзера — есть), текстовый поиск.

**Ассортимент клиента — логика с 02.09.2026 (Фаза 18, ПОЛНОСТЬЮ заменяет всё, что было раньше, включая формулировку от 01.09.2026 — если в старой переписке встретится «3 из 5 месяцев» или «разрыв ≤2», это уже не актуально)**: регулярный ассортимент товара — куплен **в обоих последних 2 месяцах** окна (подтверждает, что берут прямо сейчас) **И** минимум в **4 из последних 6 месяцев** окна (подтверждает, что покупка не разовая). Окно динамическое — всегда последние 6 из тех месяцев, что реально есть в данных (сейчас март–август); при появлении нового месяца продаж окно сдвинется само на следующей пересборке, это НЕ завязано на системную дату сервера. Тестовый ассортимент — куплен в окне хотя бы раз, но не прошёл эти условия. Товар, ни разу не купленный в окне (даже если покупался раньше) — не попадает ни в тот, ни в другой список. На реальных данных новое правило заметно строже старого: 502 позиции / ~161–164 клиента (было 1309/303 по правилу «3 из 5 + разрыв ≤2») — целенаправленно, чтобы в регулярном ассортименте оставалось только то, что клиент покупает прямо сейчас на постоянной основе, а не то, что покупал часто когда-то.

«Недопродано» (atRisk, Фаза 18) — переопределено: постоянный ассортимент МИНУС то, что уже куплено в текущем месяце (а не «не куплено в последнем месяце окна классификации», как было раньше) — явный фокус на допродажу регулярного ассортимента. Технически считается не при импорте, а динамически при КАЖДОЙ отдаче клиента (`computeAtRisk()` в `src/api.js`, вызывается из `withFreshCurrentMonth()`) — сверяет `regularAssortment` с `currentMonthItems` (отдельный поток «продажи текущего месяца», тот же что питает карточки дашборда). Плюс: обновляется сразу при загрузке свежего среза продаж текущего месяца, не дожидаясь полной пересборки всего 6-месячного ассортимента. Пока новый месяц не прислан (см. «протухание» ниже) — весь постоянный ассортимент честно показывается как «недопродано» (currentMonthItems пуст) — это корректно: в начале месяца ещё ничего не продано, ничего скрывать не нужно (раньше в этой ситуации флаг наоборот принудительно обнулялся до фактических данных — так уже не делаем). Остаток на складе — бейдж, срез на дату, есть не у всех позиций (названия усечены в 1С). Краски/оксиды — отдельная группа в обычном списке, не в «недопродано»; в карточке клиента (и в регулярном, и в тестовом ассортименте отдельно) есть переключатель «Убрать краски/оксиды», прячущий эту группу независимо от выбранного бренда. Отдельно — помесячная детализация (`monthlyAssortment`) для фильтра по конкретному месяцу в отчётах/рейтинге клиентов (не менялась, всё ещё 7 месяцев данных целиком).

«Постоянный клиент» (отдельная client-level метка, не путать с регулярным ассортиментом по товару) — купил что-либо (любой ассортимент) 3 календарных месяца подряд. Не менялась в Фазе 18.

Данные текущего месяца (`currentMonthRevenue`/`currentMonthItems`/`promotions`) автоматически обнуляются на дашборде/в API, пока новый месяц не подтверждён и не пересчитан целиком (см. `isCurrentMonthDataFresh()`/`CURRENT_MONTH_DATA_STALE_FROM` в `src/api.js`) — сам список regularAssortment/testAssortment при этом НЕ обнуляется (это историческая статистика, актуальна независимо от календаря). «Недопродано» теперь вычисляется ПОСЛЕ этого обнуления (а не обнуляется отдельным принудительным флагом, как раньше) — см. абзац выше.

**Бренды** (переопределены 01.09.2026): 5 актуальных — EPICA (префикс «E »), Kapous (префикс «HY »), Studio (префикс «S », отдельный от Kapous), AV/ES/PRO/MS (составное имя-плейсхолдер для 4 латинских префиксов av/es/pro/ms — пользователь попросил объединить их в один новый бренд и явно согласовал именно такое имя), Чистовье (всё остальное без латинской буквы в начале названия). Плюс историческая Палитра (не трогалась) и почти пустой «Прочее» (единицы позиций, где даже с латинской буквы бренд не опознан — сознательно не гадаем). Определяется по ключевым словам/префиксам в названии товара (`brand_tagging.py` в `/home/claude/gdrive-data/`), в источнике нет отдельного столбца бренда.

**Задачи — 3 независимые воронки**:
- «Визиты с супервайзером» — В работе → Выполнена (подтверждает супервайзер, этап «Архив») / Не выполнена, теги брендов + Лист ожидания/Прогрев как теги.
- «Воронка продаж» — Звонок → Встреча → Сделка/Провал; закрыть в Сделку/Провал нельзя без аудиозаписи встречи и пояснения (проверка на сервере). Провал выгружается в CSV, опционально — в Google Таблицу (код готов, сервисный аккаунт не настроен).
- «Лист ожидания» — Клиент ждёт товар → Накладная оформлена → Товар получен (подтверждает супервайзер), свои теги брендов.

Даты задач — кастомный виджет ДД.ММ.ГГ с мини-календарём. Телефон клиента виден на карточках задач во всех воронках. Заявка на перенос даты — если срок уже установлен, агент отправляет заявку, супервайзер одобряет/отклоняет. При создании новой задачи поле «Клиент» — текстовый поиск (сужает `<select>` по подстроке в названии) над самим `<select>`, а не длинный список без фильтра (Фаза 18); при редактировании клиент задачи по-прежнему заблокирован, поля поиска там нет.

**Дашборд**: сводные карточки с фильтром по агенту (клиенты, задачи сегодня, просрочено, недопродано) и по способу оплаты (долг) — оба фильтра-селекта компактного размера. (Плавающая кнопка «⬆ Наверх» была добавлена в Фазе 17 и полностью убрана в Фазе 18 — пользователь передумал сразу после сдачи, в коде её больше нет.) Дашборд агента — «Мои показатели»: «Продано всего» по умолчанию — сумма ТЕКУЩЕГО месяца, снизу чипы-фильтр по месяцам (любая комбинация — сумма и разбивка по клиентам через «/» пересчитываются на лету); топ-10 товаров по брендам (без красителей/оксидов у Kapous/EPICA); звонки/встречи сегодня. Рейтинг клиентов супервайзера (выручка/маржа/активность, фильтр по агенту и месяцу).

**Календарь**: месяц/неделя/день; встречи супервайзера с клиентом (лёгкая «бронь дня»); печать маршрута на неделю (супервайзер) — список по агентам/дням, точки внутри дня сортируются по «Номеру маршрута» клиента по возрастанию (у кого не проставлен — в конце, в исходном порядке).

**Отчёты** (супервайзер/администратор): «Ассортимент по агентам» — фильтр по бренду мультивыбором (можно отметить сразу несколько, например Kapous+EPICA+Studio), агенту («Все» тоже есть), месяцу. Отдельный трёхпозиционный переключатель «Все категории / Только краски-оксиды / Убрать краски-оксиды» сочетается с выбором бренда — например, Kapous + «Только краски/оксиды» покажет краски/оксиды именно у Kapous. Отдельный отчёт «Акции» — фильтр по агенту. Бейдж «🎁 акции» у клиента в списке + фильтр «Есть акции» видны агенту (акции текущего месяца обнуляются вместе с остальными данными месяца, пока не подтверждены заново).

**Экспорт/бэкап**:
- «Выгрузить клиентов» / «Загрузить клиентов» (страница «Команда», только админ) — пара кнопок для переноса ручных правок между пересборками. «Выгрузить» — JSON со всеми РУЧНЫМИ/бизнес-полями клиентов (адрес, телефон, конт.лицо, договор, оплата, номер маршрута, заметки, мастера, статус закрытия и т.п.), без пересчитываемых полей (ассортимент/долг/продажи месяца — они и так пересчитываются заново из файлов продаж при каждой пересборке). «Загрузить» — обратная загрузка такого файла: находит существующего клиента по имени+агенту и обновляет его ручные поля, новых клиентов не создаёт, дублей не бывает (можно загрузить один и тот же файл повторно).
- «Выгрузить задачи» (вкладка «Задачи») — как раньше, лёгкий экспорт задач для переноса между месяцами/пересборками (человекочитаемые имена клиента/агента, без вложений).
- Полный бэкап (Команда, только админ) — весь `db.json` + вложения, zip.
- CSV клиентов (супервайзер) — актуальный набор колонок.

**Прочее**: массовая перепривязка клиентов, push-уведомления (только при открытой вкладке, не настоящий web-push), «точка закрыта» — запрос агента + подтверждение супервайзера, журнал заметок по звонкам отдельно от задач, мастера точки (модель данных + карточка).

## Известные ограничения

- Регулярный ассортимент/недопродано считаются помесячно (не по дням) — приближение (см. логику выше).
- Способ оплаты и статус «по договору» — есть не у всех клиентов (нет источника в исходных таблицах).
- Обновление продаж/ассортимента/акций — по-прежнему не автоматическое, только через новую сессию с Claude и пересборку архива (нужен полный Python-пайплайн). Долги и остатки — исключение с Фазы 19: обновляются прямо через панель «Команда» (см. выше), без сессии и без пересборки, но только если файл в `.xlsx`/`.csv`. Ручные правки клиентов можно сохранить через «Выгрузить клиентов» и передать в следующую сессию (а при следующей пересборке сразу же и загрузить обратно через «Загрузить клиентов»).
- Бренд товара определяется по ключевым словам/латинским префиксам в названии (не по отдельному столбцу) — Палитра осознанно не трогалась, единичные «Прочее»-позиции не гадаем.
- На бесплатном тарифе Render данные не гарантированно сохраняются между перезапусками — нужен платный план с постоянным диском; есть кнопка ручного бэкапа.
- Нет смены пароля из интерфейса, нет email/SMS-уведомлений.
- Файловая БД рассчитана на команду до ~10-15 активных пользователей.
- Загрузка долгов/остатков через панель (Фаза 19) принимает только `.xlsx`/`.csv` — старый бинарный `.xls` нужно предварительно пересохранить в одном из этих форматов (нет LibreOffice на сервере, а сам формат `.xls` слишком сложный, чтобы разбирать его руками без библиотек). Заметьте: это ограничение только панельной загрузки в браузере — сама Claude-сессия читает присланные `.xls` через LibreOffice, который есть в песочнице (см. Фазу 20).
- Артикул товара проставлен не у всех позиций (~92%, см. выше) — нет прайса на бренд AV/ES/PRO/MS.
- «Последние продажи» на карточке клиента — это последние 3 месяца с продажами, не настоящие накладные (см. выше).

## Что заблокировано / ждёт решения пользователя

## Как работать с этим пользователем

- Присылает правки списком, по одной, ожидая, что каждая будет зафиксирована перед реализацией; даёт финальный сигнал фразой вроде «делай правки» / «делаем» / «делай все правки N» / «всё, я закончил».
- Явно просит уточнять, если что-то непонятно («если нужно уточняй, пока не получится то, что нужно») — не гадать, особенно про смысл сокращений/префиксов в названиях товаров и про пороги бизнес-логики. Если буквальная реализация правила даёт статистически странный результат (пример: Фаза 16 п.11 — правило «пауза ≤2 месяца» без минимума по числу покупок дало 39% «регулярных» позиций с одной покупкой за 5 месяцев) — показать пользователю конкретные цифры и предложенный вариант через AskUserQuestion, а не тихо доносить как есть.
- Для больших пакетов правок — сначала уточняющие вопросы через быстрый выбор (AskUserQuestion), затем при необходимости визуальный макет до кода. Пример из Фазы 17: пользователь одной фразой попросил и совместимость фильтров краски/оксиды с брендом, и обратный фильтр их скрытия, и явно попросил «задай вопросы в чат с быстрыми ответами» — 4 вопроса через AskUserQuestion сняли неоднозначность (мультивыбор vs. одиночный чип, где применять, где именно нужен обратный фильтр, детали кнопки загрузки) до начала кода.
- Если в одном вопросе несколько под-пунктов — обычно отвечает свободным текстом только на один; на остальное лучше сделать разумное предположение по умолчанию, явно написать о нём и продолжать, а не переспрашивать бесконечно. Подтверждено ещё раз в Фазе 20 (2 вопроса в одном AskUserQuestion — ответил свободным текстом только на первый про артикул, про формат «последних продаж» промолчал — сделали рекомендованный вариант по умолчанию).
- Часто присылает исходные файлы не сразу, а через сообщение-два после того, как узнаёт про ограничение («такого-то поля нет в данных») — реагировать сбором/парсингом файла сразу же, без дополнительных уточнений по формату, если он в целом похож на прежние источники (прайс-лист с колонками №/Артикул/Наименование/Цена и т.п.).
- Иногда даёт короткие правки-уточнения уже ПОСЛЕ того, как большой пакет был сдан (пример: Фаза 16 донастроила уже сданную Фазу 15) — воспринимать как нормальное продолжение работы, не как отдельный «новый проект».
- Деплой — через GitHub Desktop (Clone → скопировать файлы → Commit → Push), инструкции давать по одному шагу, ждать «готово».
- После каждого большого раунда правок: обновить README проекта, обновить статус-документ в проекте «црм » (`claude/crm-mvp-status.md`), обновить и этот файл при значимых изменениях, пересобрать zip, проверить чистую установку (импорт с нуля + curl/Playwright-проверка ключевых изменений), отправить архив.
