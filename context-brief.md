## Что это

Веб-приложение для управления задачами торговых агентов дистрибьютора косметики. Не CRM для сделок — задачник по клиентам-точкам (визиты, продажи, лист ожидания, задачи агенту).

**Стек**: Node.js без npm-зависимостей (без Express/React, всё вручную — роутер, multipart, zip), файловая БД `data/db.json` (JSON), scrypt для паролей. Фронтенд — vanilla JS/HTML/CSS, один файл `public/app.js`.

**Деплой**: GitHub Desktop → Render (https://task-ageny.onrender.com, панель — https://dashboard.render.com/web/srv-da46bcgae00c739pe5jg). Деливерабл сессии — `crm-project.zip`, собирается командой `zip -r -X crm-project.zip . -x "data/db.json" -x "data/uploads/*" -x "*.zip" -x "node_modules/*" -x ".git/*"`.

**Рабочая директория текущей сессии** (`/home/claude/crm-project`) — эфемерная песочница, не переживает сессию. Источник правды — переданный пользователю zip-архив и то, что он держит на своём GitHub (деплой на Render через GitHub Desktop). **Важно**: `data/db.json` НЕ переносится между пересборками (и в `.gitignore` — никогда не пушится на GitHub) — при новом архиве контрагенты создаются заново импортом, задачи и ручные правки клиентов иначе потерялись бы (см. кнопки экспорта ниже). **Именно поэтому любое тестирование в рабочей копии этой сессии — только на изолированной копии в `/tmp`, никогда напрямую на `data/db.json`** — см. «Технические заметки», критический урок 08.09.2026. См. также «⚠️ Прочитать первым» выше — тот же принцип, но про уже случившуюся потерю данных на реальном сервере пользователя, не про тестирование.

## Известные ограничения

## Как работать с этим пользователем

- Присылает правки списком, по одной, ожидая, что каждая будет зафиксирована перед реализацией; даёт финальный сигнал фразой вроде «делай правки» / «делаем» / «делай все правки N» / «всё, я закончил» / «делай все правки в коде» / «сделай все правки». **Не все правки идут через бэклог** — короткие прямые сообщения тоже штатный формат: команда на немедленную реализацию, без «делай правки» на отдельной строке. Пользователь часто пишет несколько поручений короткими сообщениями подряд, включая новые правки прямо во время работы над предыдущими (харнесс доставляет их как «пользователь написал, пока ты работал») — обрабатывать по очереди, не теряя ни одного, доводить каждое до полного цикла (код → проверка → документация → архив), а не молча переключаться на новое, бросив предыдущее недоделанным.
- **Слово «запиши»** — используется как самостоятельная короткая реплика вслед за только что данным поручением, напоминание не забыть задокументировать — не отмена/не блокировка реализации.
- **Слово «в константы»** (Фаза 38, новое) — просьба зафиксировать правило-исключение так, чтобы оно применялось автоматически при следующей похожей ситуации, а не решалось заново каждый раз. На практике — отдельный JSON-файл с постоянными данными (`data/import/*.json`, по образцу `client_name_aliases.json`) или именованная константа в коде, а не разовая правка только в текущем прогоне.
- **Короткое сообщение с жалобой на баг может описывать место неточно** — первая реакция: проверить БУКВАЛЬНО названное место на живом тестовом сервере; если там всё работает — искать похожие места в интерфейсе, и только при нескольких кандидатах задать один точный уточняющий вопрос (AskUserQuestion), не гадать.
- Явно просит уточнять, если что-то непонятно — не гадать, особенно про смысл сокращений/префиксов в названиях товаров и про пороги бизнес-логики. Если буквальная реализация правила даёт статистически странный результат — показать конкретные цифры через AskUserQuestion.
- Для больших пакетов правок — сначала уточняющие вопросы через AskUserQuestion, затем при необходимости визуальный макет до кода. Для маленьких точечных правок уточняющие вопросы не нужны — сразу применять по всем явно названным местам.
- Если в одном вопросе несколько под-пунктов — обычно отвечает свободным текстом только на один; на остальное лучше сделать разумное предположение по умолчанию, явно написать о нём и продолжать.
- Часто присылает исходные файлы не сразу, а через сообщение-два после того, как узнаёт про ограничение — реагировать сбором/парсингом файла сразу же.
- **Продажи агента (Фазы 38–39)**: факт = «Итого» последнего файла; файл целиком заменяет срез агента; по клиентам раскладывается как получится; при расхождении — одна короткая строка «сумма продаж N, по клиентам M», пользователь уточнит. См. `scripts/merge_agent_sales.js`, `src/agentSales.js`.
- **Несовпадения имён клиентов между агентами пользователь решает поштучно, явным ответом на каждый случай** («это разные точки», «это всегда будет так», «клиент такого-то, но сумму учитывай») — не унифицировать самостоятельно один на все случаи, каждое решение фиксировать как отдельное постоянное правило (алиас/переименование/техническая карточка), не как разовую правку данных.
- Деплой — через GitHub Desktop (Clone → скопировать файлы → Commit → Push), инструкции давать по одному шагу, ждать «готово».
- После каждого раунда правок, включая маленькие точечные: обновить README проекта, обновить статус-документ в проекте «црм» (`claude/crm-mvp-status.md` — **не обновлялся с Фазы 35, требует досборки на фазы 36–38 при следующей возможности**), обновить и этот файл при значимых изменениях, пересобрать zip, проверить чистую установку (импорт с нуля + curl/Playwright-проверка ключевых изменений), отправить архив.

## Технические заметки

- `src/db.js` — при массовых операциях (импорт, миграции) обязательно оборачивать в `db.beginBatch()`/`db.endBatch()`, иначе квадратичный рост времени записи.
- Названия месяцев — используются полными («февраль», «апрель») и на стороне Python, и на стороне Node (`MONTH_ORDER` в `src/import.js`).
- `atRisk` («недопродано») считается заново при каждой отдаче клиента в `computeAtRisk()`/`withFreshCurrentMonth()` (`src/api.js`).
- `src/fileTable.js` — свой ридер `.xlsx`/`.csv` без библиотек: ZIP-архив читается вручную, XML листа/`sharedStrings.xml` — регулярками. Поддержан только первый лист книги. **Не читает `.xls`/`.xlsb`** (Фаза 36) — для них понятная ошибка с инструкцией пересохранить как `.xlsx`; входные `.xls`/`.xlsb` от пользователя конвертировать через `soffice --headless --convert-to xlsx` (LibreOffice) перед разбором.
- `src/debtLedger.js` (Фаза 36) — парсер формата «Ведомость консигнации» (многоблочный, FIFO-датировка долга). Гочта: `parseTableFile()` уже вырезает полностью пустые строки — оффсеты внутри блока (имя клиента и т.п.) сдвинуты относительно сырых индексов из исходника на 1.
- **КРИТИЧЕСКИЙ урок про гигиену тестирования: любое воспроизведение бага, требующее «сломать» состояние базы, — только на копии в `/tmp` (`cp -r crm-project /tmp/test-copy` или через `tar`), никогда напрямую на рабочей `data/db.json`.** Для проверки, что правка данных доедет до реального сервера пользователя — «чистая установка» БЕЗ `data/db.json` (не копия рабочего `db.json`).
- **КРИТИЧЕСКИЙ урок про доставку данных: `data/db.json` в `.gitignore`, никогда не попадает на GitHub/Render.** Любая правка ТЕКУЩИХ данных обязана попасть в `data/import/*.json` (или в код) — прямая правка `db.json` рабочей копии сессии пропадёт при следующем деплое пользователя.
- Срезы продаж — `data/import/agent_sales.json` (Фаза 39; `current_month_sales.json` удалён). Раскладка: своя карточка агента → карточка другого агента с тем же именем → «нет карточки» (в сверку).
- **Загрузка среза агента**: `node scripts/merge_agent_sales.js "<Агент>" <xlsx> "01.09–25.09.26" 2026-09-25` (`.xls` сначала в `.xlsx` через LibreOffice). Заменяет срез целиком, total = «Итого», бренд/категория — из справочников ассортимента или по префиксу, печатает сверку по agents_clients.json; окончательная сверка — на старте сервера (все карточки базы).
- **Алиасы имён клиентов по агентам — `data/import/client_name_aliases.json`** (Фаза 38). Формат: `{ "<Агент>": { "<имя из файла>": { "target": "<под каким ключом писать>", "note": "..." } } }`. Используется `merge_agent_sales.js` при следующей присылке файла того же агента — новый похожий случай добавлять сюда, не в код скрипта.
- **Разбор Excel-среза продаж по агенту** — клиент жирным с итогом, под ним не жирные товарные строки, под каждой — служебная «Реализация NNNN (дата)» (пропускать, дублирует сумму), «Итого» в конце сверять с суммой по клиентам. Тип строки без сохранённой жирности определяется по соседям: если следующая строка начинается с «Реализация» — это товарная строка, иначе — клиент.
- **Чек-лист при обновлении current_month_sales.json** — 1) дубли имён СРЕДИ новых файлов (псевдонимы вроде «Частное лицо» → переименовать в «X (Агент)», записать алиасом); 2) новые имена — сверить против карточек ТОГО ЖЕ агента (не опечатка ли); 3) совпадения МЕЖДУ агентами — одинаковый адрес = тот же клиент (объединить/техническая карточка-корректировка), разные адреса = разные клиенты, не трогать без подтверждения пользователя.
