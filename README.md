# Задачник для торговых агентов (дистрибуция косметики)

Веб-приложение для управления визитами торговых агентов к контрагентам (салоны красоты, мед.клиники и т.п.): карточка клиента с данными по маршруту, регулярный ассортимент по продажам, задолженность, доска задач-визитов и вложения (фото/аудио). Работает на телефоне и компьютере через браузер.

Написано на «чистом» Node.js — **без единой внешней библиотеки** (нет ни Express, ни React, ни базы данных вроде Postgres). Это осознанное решение: приложение запускается командой `node src/server.js` без `npm install`, что сильно упрощает установку и последующую поддержку. Все данные хранятся в одном файле `data/db.json` и в папке `data/uploads/` (вложения к задачам).

## Возможности

- **Карточка контрагента**: тип точки, адрес, телефон, контактное лицо, день визита, статус «работает по договору», способ оплаты (нал/безнал/QR), ответственный агент. Эти поля редактирует **только администратор** — торговый агент видит их, но не может менять (кроме заметок).
- **Регулярный ассортимент**: список товаров, которые клиент стабильно заказывает (рассчитан по продажам за последние 7 месяцев), с пометкой «риск» у товаров, которые не заказывали в последнем доступном месяце.
- **Задолженность**: сумма долга и отметка о просрочке — подтягивается из выгрузки по должникам.
- **Доска задач** (воронка визитов): Новая задача → В работе → Выполнена / Не выполнена / Провал. Перетаскивание карточек мышью.
- **История визитов**: по каждому клиенту видно все прошлые задачи с комментариями агента.
- **Вложения к задаче**: фото (скриншоты заказов, накладных) и аудиозаписи прямо в карточке визита.
- **Роли**:
  - **Администратор** — полный доступ, управляет сотрудниками, единственный, кто редактирует основные поля карточки клиента.
  - **Супервайзер** — видит и координирует всех агентов и клиентов, как администратор, но не управляет сотрудниками и не редактирует защищённые поля.
  - **Торговый агент** — видит и работает только со своими клиентами и задачами.
- **Новые точки вне маршрута**: если агент добавляет клиента, которого не было в исходной выгрузке, точка помечается «вне маршрута» и «на согласовании» — администратор увидит её на дашборде и подтверждает.
- **Дубли при добавлении клиента**: при создании нового контрагента система проверяет совпадение по названию, адресу и телефону одновременно — если всё совпадает, предупреждает о возможном дубле.
- **Дашборд**: количество клиентов, задачи на сегодня/просроченные, клиенты с риском «отвала» ассортимента, общий долг, новые точки на согласовании, таблица этапов задач и выполнение по каждому агенту (% выполненных визитов).

## Запуск локально (для проверки)

Нужен установленный Node.js версии 18 или новее.

```bash
npm start        # запускает сервер на http://localhost:3000
```

При первом запуске (когда база пуста) приложение **само создаёт** команду и подтягивает данные контрагентов, ассортимента и долгов из `data/import/*.json` — никаких дополнительных команд вводить не нужно.

Логины по умолчанию (**обязательно смените пароли** после первого входа во вкладке «Команда»):

| Роль | Email | Пароль |
|---|---|---|
| Администратор | `admin@cosmedica.local` | `admin123` |
| Супервайзер (Александр) | `alexandr@cosmedica.local` | `super123` |
| Агент (Нагима) | `nagima@cosmedica.local` | `agent123` |
| Агент (Татьяна) | `tatiana@cosmedica.local` | `agent123` |
| Агент (Альбина) | `albina@cosmedica.local` | `agent123` |

Если нужно начать с полностью чистой базы — удалите файл `data/db.json` и перезапустите сервер (данные контрагентов/ассортимента/долгов из `data/import/` подтянутся заново, пользователи создадутся заново с паролями по умолчанию).

## Как разместить приложение в интернете, чтобы работала команда

Подробная пошаговая инструкция с прямыми ссылками — в файле **ИНСТРУКЦИЯ_GITHUB_RENDER.md**. Коротко: код заливается на GitHub, а сервис Render.com берёт его оттуда и запускает по постоянной ссылке.

**Важно про данные**: на бесплатном тарифе Render диск не сохраняется постоянно — при обновлении или перезапуске содержимое `data/db.json` и загруженные вложения (`data/uploads/`) может обнулиться. Для реальной работы (когда терять клиентов, задачи и вложения нельзя) нужен платный план Render с постоянным диском (от $7/мес) либо обычный VPS — подключение диска подробно описано в инструкции.

## Обновление данных (продажи, долги, новые контрагенты)

Приложение не подключено напрямую к Google Диску (у него нет доступа/паролей от вашего аккаунта) — обновление происходит вручную, но просто:

1. Загружайте свежие выгрузки в две папки на Google Диске, созданные для этого:
   - **папка для актуальных продаж** — файлы по продажам за новые периоды;
   - **папка для актуальных долгов** — свежая выгрузка по задолженности.
2. Напишите об этом в следующем разговоре с Claude (в этом же проекте на claude.ai) — попросите пересчитать регулярный ассортимент и долги по новым файлам.
3. Claude обновит файлы `data/import/regular_assortment.json` и `data/import/debts.json`, вы получите обновлённый архив проекта — залейте его поверх старого на GitHub (см. инструкцию, часть «Что дальше»), Render пересоберёт сайт автоматически.
4. При перезапуске сервер сам подтянет новые данные: новых контрагентов добавит, а вручную исправленные администратором карточки (адрес, телефон, договор и т.п.) не тронет — обновятся только расчётные поля (ассортимент, долг).

## Резервные копии

Все данные — это файл `data/db.json` и папка `data/uploads/`. Периодически скачивайте их с сервера (или, если используете платный диск на Render, делайте снапшот через панель Render) в надёжное место. Потеря `data/db.json` = потеря всех клиентов, задач и истории визитов.

## Структура проекта

```
src/
  server.js    — HTTP-сервер, раздача фронтенда, отдача вложений
  router.js    — минимальный роутер
  db.js        — файловая база данных (JSON)
  auth.js      — пароли (хеширование) и сессии
  api.js       — вся бизнес-логика: клиенты, задачи, вложения, пользователи
  multipart.js — разбор загрузки файлов (фото/аудио)
  import.js    — импорт/обновление контрагентов, ассортимента, долгов при запуске
public/
  index.html, styles.css, app.js  — интерфейс (без сборки, обычный JS)
data/
  db.json      — все данные приложения (создаётся автоматически)
  uploads/     — загруженные фото/аудио по задачам
  import/      — исходные данные для импорта (контрагенты, ассортимент, долги)
```

## Известные ограничения MVP

- **«Риск отвала ассортимента» — приближение, а не точный расчёт по дням.** Исходные данные о продажах помесячные (не по датам), поэтому товар помечается «риск», если его не покупали в последнем доступном месяце — это приближение к правилу «не заказывал 14+ дней», а не точный расчёт.
- **Способ оплаты** нужно проставить вручную по каждому клиенту — в исходных таблицах агентов не нашлось отдельного столбца с этими данными.
- **Статус «работает по договору»** заполнен только там, где он был в исходных таблицах (сейчас это данные по точкам Альбины); для остальных клиентов стоит «неизвестно» — уточните и укажите вручную по мере необходимости.
- Обновление продаж/долгов — не автоматическое: см. раздел «Обновление данных» выше.
- Нет смены пароля из интерфейса (пока — через переустановку пользователя администратором).
- Нет email/SMS-уведомлений о задачах.
- Файловая БД устраивает команду до ~10-15 активных пользователей и умеренного объёма данных; для более серьёзной нагрузки понадобится настоящая СУБД.

## Небольшая заметка по качеству исходных данных

При импорте обнаружено: в таблице Нагимы дважды встречается «Салон Sofiline» (одинаковый адрес, разные контакт/телефон) — похоже на дубль в исходной таблице или два контакта одной точки. Система создала одну карточку клиента; если это два разных контакта одной точки — второй телефон/имя можно дописать вручную в заметки карточки.
